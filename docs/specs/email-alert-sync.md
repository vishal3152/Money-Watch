# Email Alert Sync

## Purpose

Let the owner's bank debit/credit alert emails turn into reviewable `ImportBatch`/Transaction rows automatically, without the owner manually forwarding or pasting each one into an AI assistant. Unlike MCP statement import (`docs/specs/import.md`), there is no human present at fetch time, so Paisa-Watch itself calls an LLM to structure each alert — a deliberate, narrow exception to the MCP importer's "Paisa-Watch never pays for LLM calls" boundary (`docs/adr/0009-email-alert-sync-calls-llm-server-side.md`). The LLM call targets any OpenAI-compatible chat-completions host the owner configures (OpenRouter, OpenAI, a self-hosted Ollama server, ...) rather than being hardcoded to OpenRouter (`docs/adr/0013-provider-agnostic-llm-config-with-cloud-only-host-safety.md`).

Runs on both tiers, with different trigger mechanisms (ADR-0010, which supersedes `BUILD_PLAN_CLOUD.md` Decision 4's "ImportBatch is local-only"):

- **Local tier** (desktop Electron, self-hosted): a standalone poll process (`pnpm email-sync:poll`) on a configurable interval — see the "Known gap" note below on what starts it today.
- **Cloud tier**: a Vercel Cron job hitting a Node-runtime API route once per configured Owner — Vercel serverless has no persistent process to hold an interval. Per-Owner IMAP/LLM credentials live in Postgres (`email_sync_settings`), a deliberate, owner-approved exception to this app's local-first default of secrets-only-in-`settings.json` — see "Cloud credentials" below for the trade-off accepted.

## Behavior

- The owner configures an IMAP mailbox (host, port, username, app password — the Settings screen links to Google's App Password support doc under this field, since Gmail requires one instead of the account's real password whenever 2-Step Verification is on), an LLM base URL/model (both required) and API key (optional — a self-hosted host like Ollama needs none), and a poll interval in Settings (`/settings` → "Email Alert Sync"). All are stored in `~/.config/paisa-watch/settings.json` alongside `databasePath`, using the same merge-preserving read-modify-write as `src/config/database-settings.ts` — stored in plaintext on disk, acceptable for a local-first single-owner app.
- The poll loop runs as a **separate Node process** (`scripts/email-sync-poll-daemon.ts`, started via `pnpm email-sync:poll`), not inside the Next.js server. This app has edge middleware (`src/middleware.ts`), so Next always compiles an edge bundle in addition to the Node one; `imapflow`'s dependency chain (`@zone-eu/mailsplit`) does bare `require("stream")` calls that fail that edge bundle even though the code never runs there — confirmed by both `next dev` and `next build` failing outright when the poll loop was wired through `instrumentation.ts`'s `register()` hook. Running it as an independent process, the same pattern `scripts/prepare-database.ts` already uses, keeps it out of Next's bundling entirely. **Known gap:** nothing currently starts this process automatically — not `electron:dev`/`electron:start`, not `pnpm dev`/`pnpm start`. The owner (or a self-hosted/Docker/NAS operator) runs `pnpm email-sync:poll` as its own long-lived process today; wiring it into Electron's `main.cjs` as a sibling spawned child (alongside the existing Next server child) and into the packaged-build pipeline (`scripts/package-electron.sh`) is unbuilt follow-up work, not attempted in this slice to avoid risking the release pipeline under time pressure.
- Once running, the process fetches candidate messages from the configured mailbox's INBOX on the configured interval: every unseen message (any age) plus every message from roughly the last 6 days regardless of its `\Seen` flag — not `\Seen` alone, since the owner's own mail client/phone can mark a message read before this app ever sees it, which would otherwise skip it forever. Idempotency against reprocessing is tracked separately (below), not by the IMAP flag, so re-fetching an already-processed recent message is harmless. On Gmail (`X-GM-EXT-1`), the SEARCH also excludes Promotions and Social category mail via `X-GM-RAW` (`-category:promotions -category:social`) — those tabs are ignored blindly and never reach the classifier/LLM; non-Gmail servers skip that clause so SEARCH does not fail.
- Before the full body is ever sent to the LLM, a cheap pre-filter classifies each message from just its sender name(s) and subject line (`src/email-sync/llm-client.ts`'s `createEmailClassifier`): a binary "is this a bank/financial-institution transaction alert?" decision, with the prompt explicitly excluding telecom/ISP/utility bills, OTPs, marketing, and e-commerce mail that merely mentions amounts or "payment" the way a real bank alert does. This bounds LLM spend on a mailbox with a lot of non-bank mail — only a message classified true goes on to the full structured-output parse below. `senderName` is the message's own IMAP `From` header; when the owner manually forwarded a bank alert rather than the mailbox receiving it directly, `originalSenderName` (extracted from a "---------- Forwarded message ---------" block in the body, `src/email-sync/extract-original-sender.ts`) is also given to the classifier, which prefers it over the forwarder's own name. A message the classifier rejects is recorded `invalid` the same way a full-parse failure is (below) — never retried, never sent for the full parse.
- Each message the pre-filter passes is sent to the configured LLM (any OpenAI-compatible chat-completions host) with a fixed structured-output schema (direction, amount, currency, calendar date, masked account-number suffix, claimed institution name, description, reference, claimed available balance — all as decimal/plain strings, never pre-scaled minor-unit integers, matching `docs/specs/import.md`'s untrusted-caller invariant). The raw LLM response is validated against this schema before anything else touches it, field by field (`validateEmailAlertFields`), collecting *every* field that failed rather than stopping at the first.
- A response that doesn't validate — including one that isn't valid JSON at all, e.g. from a provider that doesn't honor the `response_format` structured-output mode — is **not** discarded: the classifier already judged this message a real bank transaction alert, so the owner almost certainly wants the Transaction. It is queued as an **unresolved alert** carrying the LLM's own values as an editable draft plus the list of invalid fields, and the owner corrects them on `/imports` (below). Nothing is written to the ledger until they do, and a bad response never crashes the rest of that poll pass.
- The validated alert's claimed institution name and account-number suffix are matched **deterministically** against existing Institutions/Accounts: the account number's last 4 digits (ignoring any non-digit mask/space/dash characters on either side, exactly like `docs/specs/import.md`'s `resolve_account`) plus a case-insensitive, exact (after trimming) institution-name match — never a "similar name" fuzzy match, consistent with this feature never guessing an Account. Exactly one match resolves the Account; zero or multiple matches leave the alert unresolved — the LLM never picks the Account (carries over `docs/specs/import.md`'s "no fuzzy or heuristic account matching... never guessed server-side" invariant).
- A resolved alert becomes one `ImportBatch` (`source: "email"`) with a single Imported Transaction, created via the same validation path `commitImport` uses (`parseDecimalToMinorUnits` against the resolved Account's actual currency, `assertValidCalendarDate`). The alert's claimed `currencyCode` must equal the resolved Account's currency or the message is recorded `invalid` (never written as the wrong currency's minor units). Claimed account-number suffixes shorter than 4 characters are rejected the same way, and the amount/balance must themselves be plain decimal strings (no thousands separators, currency symbols, or a sign the LLM added itself) or the message is recorded `invalid` rather than crashing the poll. A claimed available balance is parsed and validated but **never** stashed as the batch's `closingBalanceMinor`/`asOfDate` and never turned into a `BalanceSnapshot`/Reconciliation — unlike a statement import's closing balance, a single alert's balance reflects only the state right after that one transaction, not reliably the account's true end-of-day balance (a second alert the same day, or any transaction this feed never sees, would make it wrong). The owner reconciles an email-synced Account manually via `/accounts/[id]/reconcile`, the same as any other Account.
- ImportBatch/Transaction ids for a matched alert are derived deterministically from `(mailbox, messageUid)` so a crash between create and `markProcessed` cannot double-write on the next poll (the same primary keys are reused).
- **Idempotency is a pointer, not a row per message.** Each mailbox has one `EmailSyncCursor` (`UIDVALIDITY` + the highest IMAP UID read); a message at or below it is skipped before any LLM call. Messages are processed in ascending UID order and the pointer advances after each one, so a poll that dies partway (an unreachable LLM host) re-reads only the message it failed on, never the ones it finished. A changed `UIDVALIDITY` means the mailbox was recreated and UIDs restarted from 1, so the pointer no longer describes these messages and the mailbox is read again from the start; a UID that can't be parsed never moves the pointer (moving it on a UID of unknown position would skip real messages).
- **Only alerts that still need the owner are stored.** A matched alert's record is its `ImportBatch`; a rejected non-bank message and a cleanly imported one leave no row at all. The `unresolved` queue therefore stays the size of the owner's actual backlog rather than growing with every email ever read. Each queued alert carries the draft (the alert's fields exactly as the LLM produced them) and the fields that failed validation, so the owner never has to re-fetch the email.
- An alert is queued as unresolved when: some of its fields failed validation, its claimed `occurredAt` is implausible against the email's `Date` header, zero or multiple Accounts matched, or the amount/currency turned out to be wrong for the resolved Account's currency. Queued alerts are never retried automatically.
- **Upgrade note:** the first poll after this change starts from an empty pointer, so recently-read messages inside the IMAP fetch window are read once more (a one-time duplicate LLM cost, bounded by the fetch cap). Nothing is double-written: matched alerts reuse the same deterministic `ImportBatch`/Transaction ids, and a re-queued unresolved alert hits the `(mailbox, messageUid)` unique constraint and is counted as skipped.
- IMAP host values are rejected if they are localhost, a private/link-local IP, or (at connect time) resolve to one — so a configured mailbox cannot be turned into SSRF against the host network. This check runs unconditionally on both tiers. The LLM base URL gets an analogous check (`src/domain/llm-host-safety.ts`, `src/email-sync/assert-safe-llm-host.ts`) but — deliberately, unlike the IMAP check — **only in cloud mode** (`docs/adr/0013-provider-agnostic-llm-config-with-cloud-only-host-safety.md`): the app's own server makes this outbound call on shared infra in cloud mode, so a localhost/private target is a real SSRF risk there, but local/self-hosted mode's whole point for this setting is letting the owner point it at their own machine's Ollama on `localhost`. `llm_api_key` remains plaintext at rest (ADR-0012, ADR-0013), same as the `openrouter_api_key` column it replaced; PostgREST grants on `email_sync_settings` / `mcp_access_tokens` are revoked so the browser Data API cannot read those rows.
- Resolving a queued alert on `/imports` lets the owner correct the fields that reach the ledger (direction, amount, currency, date, description) and pick the Account, then creates the same email `ImportBatch` an automatic match would have. The corrected values are what gets imported, not what the LLM claimed. The alert's row is deleted once its `ImportBatch` exists — that batch is its record from then on. The claimed balance, reference, institution name and account-number suffix are shown as context but never edited or imported: none of them reaches the ledger (the owner picks the Account directly), so a value the LLM mangled in one of those must not block the import.
- Review, edit, Confirm All, and Undo Import for an email-sourced `ImportBatch` reuse the existing `/imports` and `/imports/[id]` screens unchanged — an email alert batch differs from a statement batch only in `source` and in always having exactly one line item. Both screens now work in cloud mode too (ADR-0010 dropped their `isCloudMode()` redirect guard).
- **Cloud trigger**: `vercel.json`'s `crons` entry calls `GET /api/cron/email-sync` (`export const runtime = "nodejs"` — see the bundling note above; a route's own runtime export builds it for Node only, unlike the runtime-agnostic `instrumentation.ts`). The route requires `Authorization: Bearer $CRON_SECRET` (Vercel's own convention: set a `CRON_SECRET` project env var, which Vercel echoes back as that header on every cron invocation), 401s otherwise. It calls `listAllEmailSyncCredentials` — deliberately not Owner-scoped, since a cron request has no session to scope to (see that function's own comment) — then runs one poll per Owner, catching each Owner's failure independently so one bad mailbox doesn't block another Owner's poll in the same invocation. Hourly (`0 * * * *`) was the original target but requires **Vercel Pro or higher** — Hobby only allows daily cron schedules, and a finer expression fails deployment outright; shipped schedule is currently daily (`0 8 * * *`) to run on Hobby. Deployment/verification steps: `docs/cron-setup.md`.
- **Cloud credentials**: the cloud tier is genuinely multi-tenant (`PRODUCT.md`), and a cron invocation has no interactive session — it must use stored credentials for every configured Owner in one run, not an interactive login. Per-Owner IMAP host/port/username/password and the LLM base URL/model/API key sit in one Postgres table (`email_sync_settings`), protected by app-layer `ownerId` filtering per query (ADR-0006 dropped RLS as the enforcement mechanism for the app's own direct-Postgres-connection queries — RLS still exists on the table as a defense against a non-superuser role, e.g. a leaked anon/authenticated key, but not against a bug in this app's own query). PostgREST privileges for `authenticated`/`anon` on `email_sync_settings` and `mcp_access_tokens` are **revoked** (`postgres/migrations/20260911120000_revoke_secret_table_api_grants.sql`) so a browser session cannot `select` those rows via the Supabase Data API. This is a materially different exposure than the local tier, where each secret sits only on that one owner's own disk. `imap_user`/`imap_password` are additionally encrypted at rest (`docs/adr/0012-imap-credentials-encrypted-at-rest-with-app-layer-key.md`): `src/domain/secret-cipher.ts` (AES-256-GCM), keyed by `EMAIL_SYNC_ENCRYPTION_KEY` (`src/config/email-sync-encryption-key.ts`), encrypted/decrypted transparently inside `PgEmailSyncSettingsRepository` — decryption happens only in that Node-side repository, never in the browser, and only when a row is actually read (a Server Action's save-merge, the settings summary, or the cron job's mailbox connection). `llm_api_key` remains plaintext — out of scope for that ADR, same as the `openrouter_api_key` column it replaced (`docs/adr/0013-provider-agnostic-llm-config-with-cloud-only-host-safety.md`).

## Invariants

- The LLM's output is validated server-side before use; an invalid or unparseable response is never written to the database.
- The LLM never determines which Account an alert belongs to — Account resolution is deterministic suffix/institution matching only; zero or multiple candidate matches never auto-select one.
- Amounts and the claimed balance are decimal strings validated against the resolved Account's actual currency, never accepted as pre-scaled minor units from the LLM. The claimed `currencyCode` must also equal that Account's currency. The claimed balance, once validated, is never turned into a `BalanceSnapshot`/Reconciliation (see Behavior above) — it exists only to satisfy the LLM's structured-output schema and confirm the alert is well-formed.
- An account-number suffix shorter than 4 characters never resolves an Account.
- A calendar date that fails `assertValidCalendarDate` is rejected before any write.
- A claimed `occurredAt` implausibly far (more than a few days, `isOccurredAtPlausible` in `src/domain/email-alert.ts`) from the email's own `Date` header is queued unresolved for the owner rather than trusted — guards against an LLM hallucinating the wrong year or a future date. Skipped when the header couldn't be parsed, never blocking a message purely for missing metadata.
- Every IMAP message is read at most once, enforced by the mailbox's sync pointer (`EmailSyncCursor`) rather than by a stored row per message.
- Nothing is stored for a message that isn't a bank transaction alert, or for one that imported cleanly — only alerts still waiting on the owner are persisted.
- A queued alert's stored draft is never trusted as valid: it is revalidated (`validateImportableEmailAlert`) against the owner's corrections before any ledger write.
- Duplicate-flagging against existing Transactions on the resolved Account follows `docs/specs/import.md`'s existing `(accountId, occurredAt, amountMinor)` rule; advisory only, never blocks the write.
- The local poll process never imports anything reachable from the Next.js app's own module graph (`src/app`, `src/middleware.ts` — no `instrumentation.ts` exists; see above) — that graph must stay buildable without `imapflow`/`mailparser`'s Node-only dependencies. The cloud cron route is the one place the Next app *does* import them, made safe by its own explicit `runtime: "nodejs"`.
- `listAllEmailSyncCredentials` (cloud) is called only from the cron route — never from a per-Owner Server Action, which must stay scoped to the signed-in Owner via the normal `PgEmailSyncSettingsRepository`.

## Persistence requirements

- `email_sync_cursors`: local SQLite (`mailbox` primary key, `uidValidity`, `lastMessageUid`, `updatedAt`) and a Postgres counterpart (`(owner_id, mailbox)` primary key). One row per polled mailbox — the whole idempotency mechanism. `EmailSyncCursorRepository` / `PgEmailSyncCursorRepository` implement `EmailSyncCursorRepositoryPort`; `getEmailSyncCursorRepository()` picks per-tier.
- `processed_email_alerts`: the owner's review queue — only `unresolved` rows are written or listed now (`id`, `mailbox`, `messageUid`, `processedAt`, `failureReason`, `alertDraftJson`, `invalidFieldsJson`), and a row is deleted once its alert becomes an `ImportBatch`. The table keeps its original name and its `status`/`importBatchId`/`parsedAlertJson` columns so rows written by earlier polls survive the change: a legacy `unresolved` row's `parsedAlertJson` is read as its draft, and legacy `matched`/`invalid` rows are simply never listed. `UnresolvedEmailAlertRepository` / `PgUnresolvedEmailAlertRepository` implement `UnresolvedEmailAlertRepositoryPort`; `getUnresolvedEmailAlertRepository()` picks per-tier.
- `import_batches` / `transactions.import_batch_id`: SQLite (unchanged) and Postgres (ADR-0010: `postgres/migrations/20260911000000_import_batches.sql`, `src/db/postgres/repositories/import-batch-repository.ts`). `ImportBatchRepository` / `PgImportBatchRepository` implement the shared `ImportBatchRepositoryPort`; `getImportBatchRepository()` now picks per-tier instead of always throwing in cloud mode. `confirmAll()` stays a deliberately non-atomic two-step write on both tiers (trust-status flip, then `BalanceSnapshot`/`Reconciliation` via the existing repositories) — see `docs/specs/import.md`'s persistence requirements for why.
- Local: IMAP host/port/user/password, LLM base URL/model/API key, and poll interval live in `~/.config/paisa-watch/settings.json` (`src/config/email-sync-settings.ts`), merge-preserving alongside `databasePath`. The last poll's outcome (`lastCheckedAt`/`lastResult`/`lastErrorMessage`) lives in the same file (`src/config/email-sync-status.ts`).
- Cloud: the same fields live in `email_sync_settings` (`postgres/migrations/20260911010000_email_sync_settings.sql`), one row per Owner (`owner_id primary key`), read/written via `PgEmailSyncSettingsRepository` (`src/db/postgres/repositories/email-sync-settings-repository.ts`) — `imap_user`/`imap_password` encrypted at rest (`docs/adr/0012-imap-credentials-encrypted-at-rest-with-app-layer-key.md`). The same repository's `getStatus()`/`setStatus()` read/write three additive columns (`postgres/migrations/20260912000000_email_sync_status.sql`: `last_checked_at`, `last_result`, `last_error_message`) for the last poll's outcome.
- `src/email-sync/check-now.ts`'s `checkEmailSyncNow()` is the shared, tested seam that runs one poll pass and records its outcome (success, or a sanitized error message — never the raw IMAP/LLM exception text, which can embed secrets); the local poll loop (`start-polling.ts`), the Vercel Cron route, and the on-demand "Check now" route below all call it instead of `runEmailAlertSyncPoll` directly, so status recording is identical across every trigger.

## HTTP and UI contract

- `/settings` → "Email Alert Sync" section, on both tiers: IMAP host/port/username/app-password, LLM base URL/model/API key, poll interval (`src/app/settings/email-sync-settings-form.tsx`, `email-sync-actions.ts` — branches on `isCloudMode()` to read/write the local file vs. the signed-in Owner's Postgres row). Secrets are never echoed back into the page after being saved — the form shows "Leave blank to keep the saved value" once one exists, never the value itself. The same section shows the last poll's status (last-checked time, success/error) once sync is fully configured, plus a manual "Check now" button.
- `POST /api/email-sync/check-now` (`export const runtime = "nodejs"`, same reasoning as the cron route below): runs one poll pass on demand for the current context — the signed-in Owner in cloud mode (401 without a session), or the local settings.json in local mode — and records the outcome via `checkEmailSyncNow()`. 400s if email sync isn't fully configured yet.
- No new review screen: email-sourced `ImportBatch` rows appear in the existing `/imports` and `/imports/[id]`, on both tiers.
- `GET /api/cron/email-sync` — the Vercel Cron entry point, `CRON_SECRET`-authenticated, cloud-only (404s outside cloud mode).
- Unresolved-alert review surface: `/imports` lists queued alerts with their `failureReason` (why the import didn't happen). Each one opens in place into a correction form (`resolve-unresolved-email-alert-form.tsx`) — Account, direction, amount, currency, date, description, with the fields the poll flagged marked — that imports the alert and drops it from the queue (`resolve-unresolved-email-alert-actions.ts` → `resolveUnresolvedEmailAlert`). The form is folded behind a "Review & import" toggle so the queue reads as a list first, and submitted values survive a validation failure (`withPersistedFormState`).

## Acceptance criteria

Landed, tested (`src/domain/email-alert*.test.ts`, `src/domain/secret-cipher.test.ts`, `src/config/email-sync-encryption-key.test.ts`, `src/email-sync/*.test.ts`, `src/domain/email-sync-cursor.test.ts`, `src/db/repositories/{unresolved-email-alert,email-sync-cursor}-repository.test.ts`, `src/db/postgres/repositories/{import-batch,unresolved-email-alert,email-sync-cursor,email-sync-settings}-repository.test.ts`, `src/db/repository-factory.test.ts`, `src/app/settings/email-sync-actions.test.ts`):

- A well-formed structured-output payload validates into a `ParsedEmailAlert`; a malformed one (bad direction, missing field, invalid date, non-object) is rejected before use.
- `parseAlertEmail` calls the injected LLM dependency with the raw email and validates its response the same way, only after its injected `classifyIsTransactionUpdate` sender/subject pre-filter returns true; a false classification stores nothing and the full-parse LLM dependency is never called for that message.
- A message at or below the mailbox's pointer is skipped without an LLM call; the pointer advances per message, restarts on a changed `UIDVALIDITY`, and is left untouched by a UID that can't be parsed.
- An LLM response with several bad fields reports all of them, and the alert is queued with the LLM's own values as a draft; the owner's corrected values (not the draft) are what the resulting `ImportBatch` carries, and the queued row is gone afterwards.
- Exactly one Account matching both the claimed institution name and account-number suffix resolves; zero or multiple candidates leave the alert unresolved. An Account with no `accountNumber` set is never matched.
- A resolved alert creates exactly one `ImportBatch` (`source: "email"`) and one `Imported` Transaction, signed by direction (credit positive, debit negative); the batch's closing balance/as-of date are always null, even when the alert claims a balance. Verified on both SQLite and Postgres.
- The same `(mailbox, messageUid)` (SQLite) / `(ownerId, mailbox, messageUid)` (Postgres) is never queued twice (DB-enforced); two overlapping polls racing on one message produce one `ImportBatch` or one queued alert, never two.
- An LLM response that fails validation — including one that isn't valid JSON at all — is queued for the owner and creates nothing on the ledger.
- `saveEmailSyncSettings` rejects a missing/invalid required field before writing anything, requires the IMAP password only on first setup (blank keeps the saved value) on both tiers — the LLM API key is never required, only the base URL and model are, and (cloud) refuses without a signed-in Owner.
- Postgres isolation: another Owner's `ImportBatch`/queued-alert/sync-pointer/credentials rows never appear in a different Owner's queries (mirrors the existing Pg suite's isolation-test convention).
- `PgEmailSyncSettingsRepository.set()` stores `imap_user`/`imap_password` encrypted (verified by reading the raw row directly, not through the repository); `get()`/`listAllEmailSyncCredentials()` decrypt transparently, and a stored value written before this change (not in the encrypted envelope format) is returned unchanged rather than rejected.

Not yet built: automatic startup of the local poll process (see "Known gap" above).
