# Duplicate imports are flagged and gated at confirm, not blocked at commit

`commit_import`/`commit_stock_import` already computed an advisory duplicate check in `stage_import`/`stage_stock_import`, but discarded it — nothing downstream ever consulted it, so re-running an MCP import against an already-imported statement silently created a second set of Transactions. We decided against blocking `commit_import` itself (rejecting the call, requiring a `confirmDuplicates: true` retry): the calling AI assistant has no reliable way to know whether it already staged-and-relayed a duplicate warning to the owner in an earlier, possibly separate, session, so a hard block at that layer either swallows legitimate re-imports or forces retries the assistant can't reliably construct. Instead, commit stays permissive — it always writes — and persists the match as a **Suspected Duplicate** flag (a nullable self-referencing FK) on the created Transaction/StockTransaction. The actual gate moves to where the owner already reviews an import: `ImportBatchRepository.confirmAll()` / `StockImportBatchRepository.confirmAll()` now refuse while any Transaction in the batch still carries an unresolved Suspected Duplicate, extending the existing single "Confirm All" CTA on `/imports/[id]` rather than introducing a second, MCP-only confirmation path.

## Considered Options

- **Reject the whole `commit_import` call, require a `confirmDuplicates: true` flag to retry.** Rejected: the caller is an AI assistant across an MCP session boundary with no guaranteed memory of a prior staging call or duplicate warning — a blocking contract there is unreliable and disconnected from the app's one owner-facing review screen.
- **Extend `trustStatus` with a third value (e.g. `FlaggedDuplicate`).** Rejected: `trustStatus` already has binary-assumption consumers (`TransactionRepository.assertEditable`, ledger badge rendering, i18n keys) whose semantics are about review/trust, not duplicate suspicion. A separate nullable FK is additive and leaves `trustStatus` untouched.
- **When a re-import matches more than one existing record, flag against the most recent match.** Rejected in favor of the earliest match: it keeps the flag pointing at the presumed original even after a later duplicate in the chain is dismissed or removed, rather than potentially pointing at another duplicate.

## Consequences

`docs/specs/import.md`'s existing invariant — "Duplicate-flagging is advisory only ... it never blocks or silently skips a `commit_import` call" — remains true for `commit_import` itself, but is no longer the whole story: `confirmAll` can now block. That spec (and its stock-import counterpart) needs updating alongside the implementation to describe the Suspected Duplicate flag, the earliest-match tie-break rule, and the new `confirmAll` precondition.
